# agent-organs · 灵魂的零件

> **`dsh-agent-soul` 是说明书，这里是零件。**
>
> 说明书告诉你「一个 agent 该怎么搭自己的灵魂」—— 五层、四条判据、一份能力清单、一次自检。
> 这个仓库装的是**真去干那些活的插件**：压缩、裁剪、推送、体检。

---

## 为什么分成两个仓库

```
dsh-agent-soul     说明书 —— 一年可能改不了几次
dsh-agent-organs   零件   —— 装着干活的，会频繁更新（本仓库）
```

三个理由：

1. **更新节奏差得远。** 判据不该跟着实现一起改版。
2. **你可以只要说明书。** 它不依赖这里任何一个零件 —— 你完全可以照着自己挑、或者自己写。
3. **每个零件都能单独用。** 它们不是「一个整体拆开的碎片」，是各自独立的插件。

## 零件清单

| 目录 | 它是谁 | 干什么 |
|---|---|---|
| `compaction/` | **压缩器** | 给压缩产物装上「门牌」—— 让压缩后的摘要能回到原话 |
| `pruner/` | **裁剪器** | 同上，装在被裁掉的工具结果上 |
| `memory/` | **热记忆** | 每轮推送一个实时时钟与一层定长自我层 |
| `echo/` | **哨兵** | 记忆中枢的实时体检台 |
| `huanqi/` | **换气** | 思考退化治理：四条判据（流内早杀 / 流末 / 重复 / 空回合），共用一本额度账 |
| `huanqi-panel/` | **换气的面板** | 在设置页里调换气参数（字节级编辑 YAML，不动注释与缩进） |
| `clock/` | **侧边栏时钟** | 把同一个时钟摆到界面上（memory 摆在提示里） |
| `mnemon-probe/` | **热记忆探针** | 每轮报磁盘状态：条数 / 字节 / 预算占比。★ 并说明自己测不到什么 |
| `riji/` | **日记** | 读一手 markdown，目录 + 原文。「读物」的代表 |
| `model-statusbar/` | **本地模型状态栏** | 本地模型服务的状态与空闲静息 |
| `mobile-adapt/` | **手机端适配** | 竖屏上收成手机形态，只加一层样式覆盖 |
| `splash/` | **启动画面** | 换启动动画与淡入淡出（播放器，不带素材） |
| `yantai/` | **工作台** | 一屏摊开：水位 / 未结的活 / 最近的账本 / 几扇门 |

**★ 「门牌」是什么，值得单独说一句：**

所有压缩、裁剪、摘要类的产物，**必须带得回原文的指针**。
没有它，压缩就是**单向的遗忘** —— 而且失败是无声的：你不会觉得丢了东西，你只是**不再想起它**。

两件事都用同一条三级纪律：

```
① 能拿到精确位置 → 写精确位置
② 拿不到        → 写「位置未知」+ 容器标识 + 一个检索入口
③ 绝不猜        → 错的门牌比没有更坏
```

第 ③ 条单独列出来，是因为**一个错的指针会让你以为能找到，于是不去找** —— 那比「找不到」坏得多。

## 怎么装

每个目录都是一个独立的 DSH 插件包，装法一样：

```bash
dsh plugin --profile <name> add <path-to-package>
# 或者从 git（改成本仓库的地址）
dsh plugin --profile <name> add github:<owner>/dsh-agent-organs
```

**装完要重启 DSH**（宿主半只在进程启动时加载一次）。
判据是**宿主里真的出现了这个包注册的东西**（工具名 / 路由 / 面板），
不是「文件复制过去了」。

## 关于这些零件的来历

它们出自一套**真实在跑的架构** —— 每一个都不是设计出来的，是**踩出来的**：

- 门牌机制，是因为**压缩过的东西再也找不回来**才加的
- 三级纪律里的第 ③ 条，是因为**写错过一次指针**才单独列出来的
- 每个阈值背后都挂着一个具体的失败 —— 答不上来「它防的是哪一次」的阈值，会在某天误伤你自己

**所以每一个包都尽量把「它防的是什么」写进注释和 README，而不只是「它做什么」。**

### 2026-10-22 · compaction 接管要两步（外部验证报告 v3 的 R2）

`compaction/HOW-TO-TAKEOVER.md` 和 `compaction/cordis.patch.yml` 同步了 soul 那边的更正。
两份文件在两边**本来就只差这一处**，所以是整份对齐，改完 diff 为 0 行。

## 改的是什么

原来写「把本包排到 bundles 最前 → 重启 → 接管」。干净沙箱实测：
**只排顺序，启动仍报**——

```
dsh-agent-compaction: Error: service "compaction" has been registered at <BasicCompactionEngine>
```

因为**排序只决定谁先注册，不决定后到的那个要不要注册**。
`compaction-basic` 还在 bundles 里、还会加载、还会去注册，所以照样撞名。
要它别注册只能显式禁掉：

```yaml
- id: compaction-basic
  disabled: true
```

判据也从一条改成两条：①启动日志里**没有** `registered` 那条错误；②探针读出 `ctor: YanqingCompaction`。
★ 只有第二条不够 —— **构造成功 ≠ 注册成功**，重名错误可以和正确的 ctor 并存。

## 一件要说清的事

**我一开始判断「这条不涉及 organs」，那是错的。**
我看了一眼 organs 的顶层目录（`clock` / `compaction` / `echo` / ...）就下了结论，
而 `compaction/` 里明明有 `cordis.patch.yml` 和 `HOW-TO-TAKEOVER.md`，
而且 patch 里就有那段「2026-10-18 结案」的注释。

★ 教训是老的：**「不涉及」也要查过才能说。**
顶层目录名叫 `compaction` 而不是 `plugins/compaction`，只说明路径不同，不说明内容不存在。

### 2026-10-22 · 同步 echo 的判据修复与 huanqi 的 peer 范围

`dsh-agent-soul` 那边收到一份外部验证报告（在云端沙箱从零装了一遍，16 条），
其中**落在零件上的四条**同步到这里。骨架结构不同（那边有 `kit/`，这边是插件本体），
所以按这边自己的路径改，不是照搬。

**① huanqi 的 peer 范围：看着更宽，实际更窄**

这边原来写 `>=0.1.2-rc.1 <0.3.0`，比 soul 那边的 `>=0.2.1-rc2` 看着宽多了。
但 semver 有一条容易忽略的规则：**带 prerelease 的比较器只对同一 major.minor.patch 的预发布版放行**。
实测：

```
satisfies('0.2.1-rc.2', '>=0.1.2-rc.1 <0.3.0')  →  false
satisfies('0.2.1',      '>=0.1.2-rc.1 <0.3.0')  →  true
```

也就是说它只认 0.1.2 那条线的 rc，**2.1 的 rc 反而进不来** —— 而 DSH 现在正是 0.2.1-rc.2。
改成 `>=0.1.2-rc.1 <0.3.0 || >=0.2.1-rc.2 <0.3.0`，两条线都收。`dsh-agent` 和 `dsh-llm` 都改。

★ 这一条和 soul 那边是**同一个坑、两种写法**：那边是 `rc2` 少了个点，这边是范围写法。
修的时候不能只改一处，得两边都验 `satisfies()`。

**② doctor 的 SELF 判据认的是工具描述**

原来：`raw.includes("自我层") || raw.includes("SELF.md")`。
可 `agent_soul_scaffold` 的工具描述里就写着 SELF 模板、SELF.md —— 工具定义会进日志，
所以**只要插件装上了**这个判据就恒真。**一个永远通过的自检比没有更坏**：它不只是不报错，
它会明确告诉你「装好了」。

改成认 SELF.md **正文里才有的**词（`四条硬线` / `## 我是谁`），工具描述不会写这两个串。

**③④ 热记忆与身份：把「还没建」显示成「没问题」**

- 热记忆：`USER.md` / `MEMORY.md` 不存在时 `bytes=null`、`pct=null`，被 `filter` 掉之后
  `worst` 是 `undefined`，`status` 停在 `ok`。现在 `bytes === null` 直接降 `warn`。
- 身份判据：`status` 写死了 `"ok"`，哪怕《墨》里一条 `lead` 都没有。
  零代 lead 不是「判据通过」，是「还没建立署名人」。现在降 `warn`。

★ 两条都是同一个毛病：**判据把「我拿不到数据」当成了「数据是好的」。**

**这边没有改的**（不是漏）：`add-bundle`、`plan` 的占位符正则、`scaffold` 干跑、
`verify-live` 的 bundle 解析 —— 那些都在 `kit/` 里，这个仓库不含 `kit`，
它们在 soul 那边已经修了。

#### 附：huanqi 的 peer 范围已完全对齐到 soul 的分段写法

上面那条只补了 `0.2.1-rc.2` 那条线，范围写法两边还是不一样。现在完全对齐了 ——
逐版本比对差异为 **0**。

★ **这次对齐是双向的，一边变宽一边变窄，值得记下来。**

| 版本 | 对齐前（organs） | 对齐后（= soul） |
|---|---|---|
| `0.1.3-alpha.2` | 拒绝 | **接受** |
| `0.1.5-alpha.1` | 拒绝 | **接受** |
| `0.1.6-alpha.1` | 拒绝 | **接受** |
| `0.1.7-rc.1` | 拒绝 | **接受** |
| `0.1.4` | 接受 | **拒绝** |
| `0.2.0` | 接受 | **拒绝** |

前四个是「soul 测过、organs 那份没写进去」的预发布线；后两个正相反 ——
organs 那个 `>=0.1.2-rc.1 <0.3.0` 靠正式版比较器把它们放行了，
而 soul 的分段写法里没有一段覆盖它们。

**所以「对齐」不等于「变得更宽」。** 如果有人正在用 `0.1.4` 或 `0.2.0`，
对齐之后会装不上 —— 那两个版本不在 soul 验过的名单里，这是有意的收紧。

★ 为什么非要对齐：同一个插件两个发行版、两套范围，是**必须靠人记住才能不出错**的状态。
现在两份 `peerDependencies` 一字不差，改一处就知道另一处也要改 ——
**能靠比对发现的问题，不该靠记忆发现。**

### 2026-10-19（同日第二次）· 判据 ④ 看错了地方：它看整轮，实际要防的是「最后一脚踩空」

**怎么发现的**：修完当天就在真实会话里撞上了。爀曦的原话：

> 「前面有正常思考和调用文件、读写，但是**到最后一步思考的时候停留在思考里了**，
> 没有再继续调用，输出，结果就是最后一步没有正文输出，这个换气没有检测到」

**错在哪**：第一版记的是「这一轮里**任何一次**产出」。而一次正常回合里，
读文件、写文件每一步都是 tool-call —— 所以只要前面动过手，最后一步卡死它就不管了。
判据 ① 也没接住：流内早杀要求思考够 3000 字才动，最后一步常常够不到。

**修法**：改成看**最后一条** assistant 消息（覆盖写入，不是 OR 累积）。
「最后一条是 tool-call」不算卡住（那是在等工具结果），只有「以纯思考收尾」才是踩空。

顺带补诊断日志：出手和不出手都留一行 `turn/end kind=… 最后一条有产出=…`
（用 debug 级，平时不输出 —— 出问题时可以调成 info）。

**验证**：测试 +2（真实形状 + 对照组），三仓 196/198/196 全过。

★ 教训：第一版 11 个用例全是「整轮有没有产出」，没有一个在前面调过工具 ——
所以全过，而真实形状一次都没被覆盖。**测试贴着实现写，就会漏掉实现想岔的方向。**
